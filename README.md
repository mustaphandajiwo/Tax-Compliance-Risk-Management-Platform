# Tax Compliance Risk Platform

An authority-neutral compliance risk management platform for **sub-national and national revenue
authorities**. Everything that differs between authorities (name and branding, time zone, currency,
administrative areas and what they are called, taxpayer-ID format, data sources, legal instruments and
effective-dated obligations, tax scope, message templates, retention) lives in a **jurisdiction pack**,
so onboarding a new authority means writing a pack, not changing code. See `docs/jurisdiction_packs.md`.

It ingests revenue records, verifies PAYE obligations against effective-dated legal versions, detects
risk signals across filing and payment, prioritises them with transparent logic and routes them to human
review. It produces **risk indicators, not findings of evasion**, and never takes outward action on its own:
no automated assessment, penalty, notice, levy, bank action or sanction exists anywhere in the system.

| Pack | Authority | Use |
|---|---|---|
| `demo` (default) | *Demo State Revenue Service* (fictional, 12 Districts) | Presenting the platform to any authority |
| `ng-niger` | Niger State Internal Revenue Service, Nigeria (25 LGAs) | Worked example of a real-jurisdiction pack |

> **All data in this repository is SYNTHETIC.** Identifiers look like `DEMO-EMP-0001`, names carry
> "Demo", and every legal parameter is a placeholder until the authority's legal officers confirm it from
> authenticated texts. Demo environments cannot send messages.

## Quick start (local, synthetic data)

Requirements: Python 3.12+, [uv](https://docs.astral.sh/uv/), PostgreSQL 16, Node 22 + pnpm.

```bash
# 1. Database roles + database
psql -U postgres -f infra/db/init.sql
psql -U postgres -c "CREATE DATABASE taxrisk OWNER taxrisk_owner"

# 2. Backend: migrate, seed the default pack, load the synthetic fixture, evaluate, verify the golden file
uv sync
uv run taxrisk demo          # prints import results, run counts and the golden comparison
uv run uvicorn taxrisk_api.main:app --port 8000      # API docs at http://localhost:8000/docs

# 3. Web console
pnpm install
pnpm dev                                            # http://localhost:3000 -> pick a demo user
```

To demonstrate a different pack: `TAXRISK_DEFAULT_PACK=ng-niger uv run taxrisk demo` (each pack is its own
tenant, so several can live in one database). `uv run taxrisk packs` lists them.

Or the whole stack in containers: `docker compose -f infra/docker-compose.yml up --build`, then
`docker compose -f infra/docker-compose.yml exec api taxrisk demo`.

```bash
uv run ruff check . && uv run ruff format --check .   # lint + format
uv run mypy                                            # types
uv run pytest                                          # unit + integration (needs local Postgres superuser)
uv run python -m scripts.benchmark_engine              # NFR-03 engine throughput
pnpm lint && pnpm typecheck && pnpm build             # web console + contracts + design packages
pnpm test:e2e                                          # Playwright + axe; needs API on :8000 (after `taxrisk demo`) and a prior build
```

The golden-file test loads the fixture through the real import pipeline, evaluates as at 2026-10-01 and
compares `rule_id + subject + period + status + hold` against `expected_findings.json`. The expectations
are declared per scenario in `fixtures/generate.py`, independently of the engine.

## Integrations

The platform connects to source systems three ways, all through the same validation, quarantine and audit
pipeline as file imports: a scheduled **pull connector** (pre-configured for a revenue collection
platform), **signed webhooks**, and a **JSON push API** for machine clients such as the e-tax portal or
employer payroll systems. Connecting a real platform is a mapping change, not new code. See
`docs/integrations.md`, including what the collection-platform vendor needs to provide.

Third-party sources (company registries, licensing registers, pension regulators and similar) can be added the same way once a
data-sharing basis is recorded. Social-media monitoring is deliberately not supported: it falls outside
the lawful-data scope and cannot meet the platform's evidence standard.

## Key design choices

- **Rules first, no black box.** 12 deterministic rules in a closed JSON DSL; no arbitrary code, no ML,
  no generative AI anywhere in scoring. See `docs/decisions/0002-restricted-rule-dsl.md`.
- **Unknown is not non-compliant.** A missing filing counts only when filing coverage for the period is
  complete; event time is used, never ingestion time; an obligation without an approved legal version
  is *unverified*, which becomes a hold.
- **Hard stops.** Stale data, uncertain identity, unverified obligations or undecided extensions turn a
  signal into a review / data-quality item with no culpability score. Appeals and stays keep the score
  visible but block outward action.
- **Separate dimensions.** Likelihood (1-5), consequence (1-5 or *unknown*, never guessed), confidence
  (0-1, shown separately) and effort. Priority = 4 x L x C exists only to order a queue.
- **Reproducible.** Every finding stores the rule version, legal version, tax period and input snapshot.
  `POST /api/v1/risks/{id}/reproduce` recomputes it bit-for-bit.
- **Governed change.** Rule versions need a backtest, a legal approval and a compliance-manager approval
  from two people other than the author; approved versions are immutable in the database.
- **Isolation.** One authority per installation (single-tenant hosting). Every tenant table carries `tenant_id` with forced
  Postgres row-level security; a test-only organisation exists only inside the test suite to prove it.

## Rule codes

The PRD and the Technical Specification used the same codes for different rules. This build adopts the
Tech Spec section 23 pilot-pack meanings and renumbers colliding PRD rules so that no code ever has two
meanings. The mapping is in `docs/legal_config/rule_catalogue.md`.

## Before production

This repository delivers a working, tested platform on synthetic data. Going live still needs the
discovery and pilot work for the adopting authority: legal sign-off of every obligation and
deadline from authenticated texts, real source extracts and data-sharing agreements, a confirmed
operational definition of "active employer", evidence-confidence thresholds set from shadow-mode profiling,
named approvers, a hosting/data-residency decision, penetration testing and a rehearsed restore. See
`docs/operations.md` and `docs/security.md`.

## Origin

The platform was first specified for one state revenue service (the `ng-niger` pack). Its requirements
trace back to that PRD and Technical Specification (`docs/requirements_traceability.md`). The one deliberate
departure is that authority-specific facts were moved out of code into jurisdiction packs so the same
product can be presented to, and run by, other authorities.
